# 🧠 1️⃣ Project Architecture (Django Apps Structure)

Do NOT put everything in one app.

Structure it like this:

```
core/              → shared utilities
accounts/          → users & shop profiles
requests_app/      → item requests
responses/         → “I Have It” responses
chat/              → private messaging
moderation/        → reports & flags
notifications/     → in-app notifications
```

This keeps your project clean and scalable.

# 🗄 2️⃣ Database Models (Clean & Practical)

## 🔹 accounts app

### User (extend AbstractUser)

* id
* phone_number
* is_approved (Boolean)
* is_suspended (Boolean)
* report_count (Integer)
* date_joined

### ShopProfile

* user (OneToOne → User)
* shop_name
* location_description
* created_at

---

## 🔹 requests_app

### ItemRequest

* id
* owner (FK → User)
* category (choices)
* brand
* model
* description
* image
* status (Active / Negotiating / Bought / Cancelled)
* created_at
* updated_at

Important:
Default status = Active

---

## 🔹 responses

### ItemResponse

This represents someone clicking "I Have It".

* id
* request (FK → ItemRequest)
* responder (FK → User)
* created_at

Constraints:

* Unique together: (request, responder)
  → So one user cannot click “I Have It” twice.

---

## 🔹 chat app

We do conversation-based messaging.

### Conversation

* id
* request (FK → ItemRequest)
* buyer (FK → User)  → request owner
* seller (FK → User) → responder
* is_active (Boolean)
* created_at

Important:
Only created when owner chooses a responder.

---

### Message

* id
* conversation (FK → Conversation)
* sender (FK → User)
* content
* created_at
* is_read (Boolean)

---

## 🔹 moderation app

### UserReport

* id
* reported_user (FK → User)
* reported_by (FK → User)
* reason
* created_at

Logic:
Every time report created:
→ Increase reported_user.report_count

# 🔄 3️⃣ Request Flow Logic (Very Important)

Here’s how the system behaves:

---

### Step 1: User posts request

Creates:
ItemRequest (status = Active)

---

### Step 2: Other users click “I Have It”

Creates:
ItemResponse

Publicly visible list:

* Shop A
* Shop B
* Shop C

---

### Step 3: Owner selects one responder

When owner clicks “Start Chat”:

Check:
Does Conversation already exist for (request + seller)?

If NO → create Conversation
If YES → redirect to existing chat

---

### Step 4: Negotiation

Messages created inside Conversation.

Other responders remain visible but no private access.

---

### Step 5: Owner marks status

If Bought:

* request.status = Bought
* request removed from active timeline

If Negotiating:

* status = Negotiating

---

# 🚦 4️⃣ Timeline Logic

When showing homepage:

Only show:

```
ItemRequest.objects.filter(status="Active")
```

Optionally show Negotiating separately.

Never show Bought in main feed.

# ⚖️ 5️⃣ Moderation Logic

When report created:

```
if user.report_count >= 5:
    send_warning_notification()

if user.report_count >= 10:
    user.is_suspended = True
```

Later:
Celery Beat can run daily to:

* Auto suspend flagged users
* Auto delete old requests (30 days)
